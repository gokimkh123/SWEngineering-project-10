## 1. 문서 개요 (Introduction)

### 1.1 목적 (Purpose)

이 문서는 "찰칵부산"의 기능·품질 요구사항을 정의하며 설계·구현·테스트와 평가의 기준이 된다. 요구사항은 경쟁 서비스 분석·브레인스토밍(이슈 #1~#4)·화면 시안으로 도출했고, 설문·인터뷰 결과는 최종 요구사항정의서(v2.0)에 반영한다.

### 1.2 프로젝트 범위 (Scope)

찰칵부산은 사진을 "여기가 어디?"라는 이미지 질의로 받아 부산 공식 데이터로 장소를 찾고, 장소 정보·근처 명소·동선 지도와 출처 각주가 붙은 여행기를 제공하는 부산 지역 안내 모바일 웹 서비스다.

| 구분 | 포함 기능 |
|---|---|
| MVP 필수 (Must) | 사진 업로드·EXIF 분석, 방문지 묶기, 장소 매칭, 사용자 확인, 동선 지도, 장소 상세(출처), 여행기 생성 |
| 권장 (Should) | 위치 없는 사진 처리, 공유 카드, 근처 못 가본 곳 추천 |
| 선택 (Could) | 문단 다시 쓰기·사실 대조 경고 |
| 범위 밖 | 회원 가입·로그인(익명 기기 토큰으로 대체), 소셜 기능, 결제, 다국어 여행기, 부산 외 지역, 네이티브 앱 |

### 1.3 용어 및 약어 (Definitions & Acronyms)

| 용어/약어 | 정의 |
|---|---|
| LLM / VLM | 대규모 언어 모델 / 이미지와 텍스트를 함께 이해하는 모델 |
| EXIF | 사진 파일에 저장된 촬영 시각·GPS 좌표 등 촬영 정보 |
| 방문지 (Visit) | 시간·거리가 가까운 사진을 DBSCAN으로 묶은 단위. 실제 장소 하나에 대응 |
| closed-set 매칭 | AI가 공식 데이터로 찾은 후보 목록 안에서만 장소를 고르는 방식 |
| 확신도 | VLM이 고른 장소가 맞을 가능성(0~1) |
| 평가셋 | 정확도 측정용 팀 촬영 사진과 정답 라벨(방문지 20곳 이상). 임계값 조정용 사진과 분리 |
| 익명 기기 토큰 | 회원 가입 없이 기기마다 발급해 "내 여행"을 구분하는 값 |

## 2. 전체 설명 (Overall Description)

### 2.1 제품 관점 (Product Perspective)

공공데이터·지도·AI API와 연동하는 독립형 모바일 웹 서비스다. 흐름: 사진 업로드 → EXIF 추출 → 방문지 군집화 → 후보 조회 → VLM 판별(애매하면 사용자 확인) → 동선·장소 상세 → 각주가 붙은 여행기 → 공유 카드

### 2.2 대상 사용자 (Target Users)

| 사용자 유형 | 특징 | 주요 목표 | 권한/제약 |
|---|---|---|---|
| 국내 여행자 (주 사용자) | 20~30대, 부산 1~3일 여행. 페르소나 지민(23세, 1박 2일 사진 200장 중 블로그에 3장 올리고 멈춤) | 사진만 올려 장소·동선을 정리하고 여행기 남기기 | 익명 기기 토큰으로 자기 여행만 조회·수정·삭제 |
| 외국인 관광객 | 한글 지명 검색이 어려움 | 다국어 여행기 | 2단계 (MVP 범위 밖) |

### 2.3 운영 환경 (Operating Environment)

- Client: 모바일 웹 브라우저(iOS Safari, Android Chrome 최신 버전), 데스크톱 브라우저
- Server: Docker Compose — FastAPI 서버, Python 분석 워커, 오픈소스 VLM 추론 서버
- External AI/API: LLM API(Claude Haiku 또는 Gemini 무료 플랜), TourAPI, 부산광역시 명소·맛집 API, 카카오 지도·로컬
- Database: PostgreSQL (장소 캐시 포함)

### 2.4 제약사항 (Constraints)

- 과제 조건: LLM·VLM과 부산 공공데이터·API를 쓰고, 군집화·후보 검색·라우팅·각주 연결은 자체 코드로 구현한다
- 이용조건: 출처·공공누리를 표시하고, 카카오 로컬 결과는 운영정책상 장소 ID·URL만 저장한다
- 개인정보: AI 분석 전 동의, 사진은 서버의 VLM으로만 분석(외부 AI 미전송), 원본·좌표는 분석 후 삭제, 인물 미분석
- 비용·한도: 공공데이터 쿼터(TourAPI 일 1,000회 등) 안에서 동작하고, AI는 오픈소스 VLM과 저가·무료 LLM을 쓴다
- 범위·일정: 테스트 사진은 팀 촬영본만, 결제·예약은 범위 밖. 중간발표 10/29, 코드 프리즈 11/27, 최종발표 12/1·3

### 2.5 가정 및 의존성 (Assumptions & Dependencies)

- 사진 대부분에 GPS가 있다(없으면 FR-06·FR-02로 대응). 모바일 웹 업로드의 GPS 유지는 스프린트 1 실기기 PoC로 확인한다
- 주요 관광지·음식점은 TourAPI·부산시 데이터·카카오 로컬에 있고, 외부 API의 형식·무료 쿼터가 개발 기간 동안 유지된다
- VLM 모델, 군집화·확신도 임계값은 기술 PoC 후 확정한다

## 3. 기능 요구사항 (Functional Requirements)

| ID | 요구사항명 | 요구사항 내용 | 우선순위 | 검증 방법 | 비고 |
|---|---|---|---|---|---|
| FR-01 | 사진 업로드·EXIF 추출 | 사용자는 사진 1~30장(JPEG·HEIC·PNG, 장당 20MB 이하)을 올리고, 시스템은 촬영 시각·GPS를 추출해 "위치 있음 N장 · 없음 M장"으로 보여야 한다. 30장 초과는 막고 지원하지 않는 형식·20MB 초과 사진은 제외하고 안내한다. | Must | Test | UC-01 · AC-01 |
| FR-02 | 방문지 자동 군집화 | 시스템은 촬영 시각·좌표에 DBSCAN을 적용해 사진을 방문지로 묶고 방문 순서·사진 수·중심 좌표·시간대를 날짜별로 계산해야 한다. 위치 있는 사진이 없으면 촬영 시각으로 묶고 모두 선택필요로 둔다. | Must | Test | UC-01 · AC-02 |
| FR-03 | 공식 데이터 후보 조회 | 시스템은 방문지 반경 300m(없으면 600m) 안의 장소를 TourAPI, 부산광역시 명소·맛집 데이터, 카카오 로컬(음식점·카페 보조)에서 찾아 후보 2~3곳을 제시하고, 없으면 사용자 선택으로 넘겨야 한다. 공공데이터 결과는 캐시하고 카카오 결과는 장소 ID·URL만 저장한다. | Must | Test | UC-02 · AC-03 |
| FR-04 | VLM 후보 판별·확신도 산출 | 시스템은 대표 사진 1장과 후보 목록을 VLM에 보내 장소 ID·확신도(0~1)·근거를 받아야 한다. 확신도 0.8 이상 자동 확정, 0.5 이상 0.8 미만 사용자 확인, 0.5 미만 사용자 선택으로 처리한다(8장). | Must | Test / AI 평가 | UC-02 · AC-04 |
| FR-05 | 사용자 확인·수정 | 사용자는 확인이 필요한 방문지에서 사진·후보·AI 추천과 근거를 보고 장소를 고르거나, 직접 검색하거나, "기타 장소"(방문지 중심 좌표)로 저장할 수 있어야 한다. 자동 확정도 바꿀 수 있고, 결과는 매칭 로그(DR-09)로 남긴다. | Must | Test | UC-02 · AC-05 |
| FR-06 | 위치 없는 사진 처리 | 시스템은 GPS 없는 사진의 촬영 시각이 앞뒤 방문지 사이면 그 방문지를, 애매하면 VLM으로 인접 사진과 비교해 추천하고, 배정은 사용자가 확인한다. | Should | Test | UC-03 · AC-13 |
| FR-07 | 지도 동선·타임라인 | 시스템은 확정된 방문지를 카카오맵에 방문 순서대로 핀·경로로 표시하고 이동 시간을 타임라인으로 보여 주며, 날짜별·전체 보기를 전환할 수 있어야 한다. | Must | Test | UC-04 · AC-06 |
| FR-08 | 장소 상세 | 사용자가 방문지를 누르면 시스템은 공식 데이터의 개요·주소·대표 사진·출처·갱신일을 보여 줘야 한다. 카카오 장소는 이름·주소를 실시간 조회하고 카카오 장소 페이지로 연결한다. | Must | Test | UC-05 · AC-14 |
| FR-09 | 근거 기반 여행기 생성 | 시스템은 확정 방문지·공식 정보·선택한 문체로 LLM 여행기(제목, 본문, 날짜별 동선 요약)를 만들고, 장소 이름을 장소 ID와 연결하며, 사실 문장마다 출처 각주와 AI 작성 표시를 달아야 한다. | Must | Test / AI 평가 | UC-06, UC-09 · AC-07 |
| FR-10 | 문단 다시 쓰기·사실 대조 경고 | 사용자는 여행기 문단을 골라 다시 생성할 수 있어야 하고, 편집한 문장이 공식 데이터와 다르면(운영시간, 위치 등) 시스템이 경고해야 한다. | Could | Test | UC-07, UC-09 |
| FR-11 | 공유 카드 생성 | 시스템은 대표 사진·제목·동선 요약으로 공유 이미지를 만들되 좌표·정확한 위치 정보는 넣지 않아야 한다. | Should | Test | UC-08 · AC-10 |
| FR-12 | 근처 못 가본 곳 추천 | 시스템은 방문지 주변 공식 데이터 장소 중 가지 않은 곳 2~3곳을 거리순으로 이름·유형·거리·출처와 함께 안내해야 한다. | Should | Test | UC-04 · AC-17 |

### 5.2 Use Case 명세

| Use Case ID | UC-01 |
|---|---|
| 이름 | 사진 업로드·방문지 분석 |
| Actor | 여행자 |
| 사전조건 | 부산 여행 사진이 갤러리에 있고, 사진을 AI로 분석하는 데 동의했다 (NFR-04) |

| DR-02 | Visit (방문지) | 시스템 생성 | DB: 장소, 시각, 확신도, 순서, 중심 좌표(소수점 4자리), 상태(분석중·자동확정·확인필요·선택필요·확정·기타장소) | 사용자 삭제 시까지 |

DR-08 (데이터 처리 원칙): 원본 사진은 분석에만 쓰고 자동 삭제하며, 화면에는 EXIF를 뺀 썸네일만 쓴다. 사진 좌표는 방문지 중심 좌표(소수점 4자리)를 계산한 뒤 삭제하고, 외부 데이터는 제공처·갱신일과 함께 표시한다.

## 8. AI 관련 요구사항 (LLM/VLM)

AI는 후보 중 장소 판별(VLM — 서버에서 실행하는 오픈소스 모델)과 확정된 사실로 여행기 작성(LLM — 저가 모델 또는 무료 플랜)에만 쓰고, 나머지는 코드로 구현해 재현·테스트할 수 있게 한다.

| AI 요구 ID | 항목 | 요구사항 | 검증/평가 방법 | 비고 |
|---|---|---|---|---|
| AIR-01 | 입력 구성 | VLM 입력은 대표 사진 1장(축소본)과 후보 목록(이름·유형·거리·개요·사진, 카카오 후보는 이름·유형·거리만)이다. | Review (프롬프트·코드) | FR-04 |
| AIR-02 | 근거 기반 응답 (closed-set) | VLM은 후보 안에서만 고르고 없으면 "없음"을 답하며, 응답은 장소 ID·확신도·근거의 정해진 JSON이다. | Unit Test (스키마) | FR-04 |
| AIR-03 | 실패 처리 | 후보 밖 ID·형식 오류는 거부 후 1회 재요청하고, 다시 실패하면 사용자 선택으로 넘긴다. 장애는 사용자에게 안내한다. | System Test (장애 주입) | FR-04, FR-05 |
| AIR-04 | 안전/개인정보 | VLM은 사진 속 인물을 분석하거나 설명하지 않는다. | Review / Test | FR-04, NFR-04 |
| AIR-05 | 근거 기반 생성 | LLM에는 확정 방문지·공식 데이터만 {장소 ID, 필드} 구조로 넣고, 문장마다 근거 장소 ID·필드를 표시하게 한다. | 평가 Test Set | FR-09 |
| AIR-06 | 사실 대조 | 여행기의 장소 ID와 문장 속 이름·숫자·시간을 입력 필드 값과 코드로 대조하고, 근거 없는 사실 문장은 경고·제거한다. | Unit Test | FR-09, FR-10 |
| AIR-07 | 비용 관리 | 방문지당 대표 사진 1장만 축소해 VLM에 넣고, 판별 결과를 저장해 다시 호출하지 않는다. | Review (호출 로그) | FR-04 |
| AIR-08 | 평가·버전 관리 | 프롬프트는 버전을 붙여 관리하고, 평가셋으로 매 스프린트 정확도를 측정한다(DR-09). | AI Evaluation (NFR-02) | 전체 |

## 9. 인수 기준 (Acceptance Criteria)

형식: 조건 → 행동 → 결과. 시연 시나리오는 팀원이 촬영한 부산 1박 2일 사진 24장(위치 있음 21, 없음 3)이고, 정확도(AC-04)는 별도 평가셋으로 잰다.

| AC ID | 기준 | 관련 요구사항 | 확인 방법 |
|---|---|---|---|
| AC-01 | 24장을 올리면 위치 있음 21장·없음 3장이 표시된다. 31장은 막히고, 지원하지 않는 형식·20MB 초과 사진은 제외되며 안내가 나온다. | FR-01 | Acceptance Test |
| AC-02 | 위치 있는 21장이 정답 라벨과 같은 6개 방문지로 묶이고(사진별 배정 일치) 날짜별로 나뉜다. | FR-02 | Acceptance Test |
| AC-03 | 방문지마다 반경 300m(없으면 600m) 안의 공식 데이터 후보가 출처와 함께 표시된다. | FR-03 | Acceptance Test |
| AC-04 | 평가셋 매칭 결과 방문지 단위 정확도가 80% 이상, 후보 포함률이 90% 이상이다. | FR-04, NFR-02, AIR-02 | AI Evaluation |
| AC-05 | 확인필요(0.5 이상 0.8 미만)·선택필요 방문지만 확인 화면에 나오고, 후보 선택·직접 검색으로 확정하면 동선이 갱신된다. 후보에 없으면 기타 장소로 저장할 수 있다. | FR-05 | Acceptance Test |
| AC-06 | 확정 후 지도에 방문 순서대로 핀·경로가 보이고 1일차·2일차 전환이 된다. | FR-07 | Acceptance Test |
| AC-07 | 여행기에 확정된 장소만 나오고, 사실 문장 전부에 각주가 붙으며, AI 작성 표시가 보인다. | FR-09, NFR-03, AIR-05 | AI Evaluation / Review |
| AC-08 | 사진 20장 분석이 1분 안에 방문지 확인 단계까지 끝난다. | NFR-01 | Performance Test |
| AC-09 | 동의해야 분석이 시작되고 외부 API 호출 기록에 사진이 없다. 분석 후 원본·좌표가 남지 않고 썸네일에 EXIF 위치가 없으며, 여행 삭제 시 관련 데이터가 지워진다. | NFR-04, DR-08 | System Test |
| AC-10 | 공유 카드 이미지에 좌표·정확한 위치 정보가 없다. | FR-11 | Acceptance Test |
| AC-11 | 팀 외 사용자 5명이 안내 없이 업로드부터 여행기까지 5분 안에 마친다. | NFR-05 | Usability Test |
| AC-12 | iOS Safari·Android Chrome 실기기에서 주요 흐름(A2~D2)이 동작한다. | NFR-06 | 실기기 Test |
| AC-13 | 위치 없는 사진 3장마다 추천 방문지와 이유가 표시되고, 확인하면 배정된다. | FR-06 | Acceptance Test |
| AC-14 | 핀·카드를 누르면 공공데이터 장소는 개요·주소·사진·출처·갱신일이, 카카오 장소는 실시간 이름·주소와 카카오 링크가 표시된다. | FR-08 | Acceptance Test |
| AC-15 | 저장소·배포 코드에 서버 API 키가 없고, 카카오맵 JavaScript 키에 도메인 제한이 있다. | NFR-07 | Review |
| AC-16 | 외부 API 장애를 모의로 일으키면 그 방문지만 선택필요가 되고 나머지 분석은 끝까지 진행된다. | NFR-08 | System Test |
