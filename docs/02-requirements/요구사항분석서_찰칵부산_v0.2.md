## 1장. 문서 개요

### 1.1 목적
이 문서는 부산 여행 사진을 분석해 방문지·동선·여행기를 만들어 주는 서비스 "찰칵부산"이 갖춰야 할 기능과 품질 조건을 정의한다. 팀원은 이 문서를 기준으로 유스케이스, 아키텍처, 구현, 테스트를 진행하며, 교수자와 평가자는 이 문서로 개발 범위와 완료 여부를 판단한다.

### 1.2 범위
찰칵부산은 사용자가 부산 여행 후 갤러리 사진을 올리면 다음을 수행하는 모바일 웹 서비스이다.

1. 사진의 촬영 시각·위치(EXIF)를 읽어 방문지별로 묶는다.
2. 방문지 주변의 공식 관광 데이터(TourAPI, 부산광역시 데이터, 카카오 로컬)에서 후보 장소를 찾는다.
3. VLM이 후보 중 사진과 맞는 장소를 고르고, 애매하면 사용자에게 확인받는다.
4. 확정된 방문지로 지도 동선과 출처 각주가 붙은 여행기를 만든다.

| 구분 | 포함 기능 |
|---|---|
| MVP 필수(M) | 사진 업로드·EXIF 분석, 방문지 묶기, 장소 매칭, 사용자 확인, 동선 지도, 여행기 생성 |
| 권장(S) | 위치 없는 사진 처리, 장소 상세(출처), 공유 카드 |
| 선택(C) | 문단 다시 쓰기·사실 대조 경고, 근처 못 가본 곳 추천 |
| 범위 밖 | 회원 가입·로그인(익명 기기 토큰으로 대체), 회원 간 소셜 기능, 결제(프리미엄 구독·포토북), 영어 등 다국어 여행기(2단계), 부산 외 지역, 네이티브 앱 |

### 1.3 용어 정의
| 용어 | 정의 |
|---|---|
| EXIF | 사진 파일에 저장된 촬영 정보(촬영 시각, GPS 좌표 등) |
| 방문지(Visit) | 시간·거리가 가까운 사진들을 하나로 묶은 단위. 하나의 실제 장소에 대응 |
| 군집화 | 사진을 방문지 단위로 묶는 처리. DBSCAN 알고리즘 사용 |
| 후보 장소 | 방문지 중심 좌표 반경 안에서 공식 데이터로 찾은 실제 장소 목록 |
| closed-set 매칭 | AI가 자유롭게 추측하지 않고, 주어진 후보 목록 안에서만 장소를 고르는 방식 |
| 확신도 | VLM이 고른 장소가 맞을 가능성을 0~1로 나타낸 값 |
| VLM | 이미지와 텍스트를 함께 이해하는 AI 모델(Vision-Language Model) |
| LLM | 텍스트를 생성하는 대규모 언어 모델 |
| TourAPI | 한국관광공사가 제공하는 관광정보 공공 API |
| 각주 | 여행기의 사실 문장에 붙는 출처 표시(데이터 제공처·갱신일) |
| 공공누리 | 공공저작물 이용 조건 표시 제도 |

### 1.4 참고 문서

- 한국관광공사 TourAPI, 부산광역시 명소·맛집 정보 API 명세 (공공데이터포털)
- 카카오 디벨로퍼스 지도·로컬 API 문서

### 1.5 문서 구성
2장 전체 설명, 3장 기능 요구사항, 4장 비기능 요구사항, 5장 유스케이스(별도 담당), 6장 UI/UX 요구사항, 7장 데이터 요구사항, 8장 AI 요구사항, 9장 인수 기준, 10장 추적표(별도 담당).

## 2장. 전체 설명

### 2.1 제품 배경
- **P1 정리되지 않는 사진**: 여행 중 하루 수십 장을 찍지만 대부분 정리되지 않고 "여기 어디였지?"만 남는다.
- **P2 기록의 수고**: 장소 검색, 정보 확인, 동선 정리, 글쓰기를 모두 직접 해야 한다.
- **P3 사진과 지역 정보의 단절**: 사진 앱은 날짜·위치까지만 정리하고, 범용 AI는 사진 속 장소를 추측해 틀리거나 출처를 대지 못한다.

### 2.2 제품 기능 요약
사진 업로드 → EXIF 추출 → 방문지 군집화 → 공식 데이터 후보 조회 → VLM 장소 판별(애매하면 사용자 확인) → 동선 지도·타임라인 → 출처 각주가 붙은 여행기 → 공유 카드

### 2.3 사용자 특성
| 사용자 | 특성 | 주요 요구 |
|---|---|---|
| 국내 여행자 (주 사용자) | 20~30대, 스마트폰 사용 능숙, 부산 1~3일 여행 | 사진만 올리면 장소·동선이 정리되는 것 |
| 외국인 관광객 (2단계) | 한글 간판·지명 검색이 어려움 | 공식 정보가 붙은 다국어 여행기 (MVP 범위 밖) |

대표 페르소나: 지민(23세, 대학생, 친구 셋과 부산 1박 2일, 사진 200장 중 블로그에 세 장 올리고 멈춤)

### 2.4 운영 환경
- 클라이언트: 모바일 웹 브라우저(iOS Safari, Android Chrome 최신 버전), 데스크톱 브라우저에서도 동작
- 서버: FastAPI 기반 API 서버, Python 분석 워커, PostgreSQL
- 외부 서비스: TourAPI, 부산광역시 API, 카카오 지도·로컬 API, 멀티모달 LLM API
- 사용자 구분: 회원 가입 없이, 기기마다 발급하는 익명 기기 토큰으로 "내 여행" 목록을 구분한다

### 2.5 설계·구현 제약사항
- LLM 또는 VLM을 반드시 활용한다 (과제 필수 조건).
- 부산 지역의 실제 공공데이터 또는 API를 활용한다 (과제 필수 조건).
- 단순 LLM API 호출만으로 구성하지 않는다. EXIF 처리, 군집화, 후보 검색, 확신도 라우팅, 각주 연결은 자체 코드로 구현한다.
- GitHub 기반으로 개발하고, 데이터 출처와 이용조건을 명시한다.
- 공공데이터 개발계정 쿼터(TourAPI 일 1,000회 등) 안에서 동작해야 한다.
- 원본 사진과 좌표는 분석 후 보관하지 않는다.
- 일정: 요구사항·설계 문서 10/26, 코드 프리즈 11/27, 최종발표 12/1·3.

### 2.6 가정 및 의존성
- 사용자의 사진 대부분은 GPS 정보를 포함한다. (메신저로 받은 사진은 위치가 지워질 수 있음 → FR-06으로 대응)
- 부산의 주요 관광지·음식점은 TourAPI 또는 카카오 로컬에 등록되어 있다.
- 외부 API의 응답 형식과 무료 쿼터가 개발 기간 동안 유지된다.
- 사용할 VLM 모델은 기술 PoC 후 결정한다. `[확인 필요]`

### 3.2 기능 요구사항 상세

**FR-01 사진 업로드·EXIF 추출 (M)**
- 입력: 사용자가 갤러리에서 고른 사진 1~30장 (JPEG, HEIC, PNG)
- 처리: 각 사진에서 촬영 시각과 GPS 좌표를 추출한다. 30장을 넘으면 업로드를 막고 안내한다. 지원하지 않는 형식은 제외하고 알린다.
- 출력: 사진별 촬영 시각, 위치 유무, 좌표 / "위치 있음 N장 · 없음 M장" 요약
- 예외: 촬영 시각도 위치도 없는 사진은 "정보 없음"으로 표시하고 분석에서 제외할지 사용자에게 묻는다.

**FR-02 방문지 자동 군집화 (M)**
- 입력: FR-01에서 추출한 시각·좌표
- 처리: 시간 차와 거리 기준으로 DBSCAN을 적용해 사진을 방문지로 묶고, 방문지별 중심 좌표·시작·종료 시각을 계산한다. 날짜별로 1일차, 2일차를 나눈다.
- 출력: 방문지 목록 (방문 순서, 사진 수, 중심 좌표, 시간대)
- 기준값: 거리·시간 임계값은 PoC 후 확정 `[확인 필요]`

**FR-03 공식 데이터 후보 조회 (M)**
- 입력: 방문지 중심 좌표
- 처리: 반경 300m 안의 장소를 TourAPI 위치기반 조회로 찾고, 카카오 로컬로 음식점·카페를 보조 검색한다. 후보가 없으면 600m로 확대한다. 그래도 없으면 "기타 장소"로 처리한다. 조회 결과는 장소 캐시에 저장해 같은 장소를 반복 조회하지 않는다.
- 출력: 방문지별 후보 장소 2~3곳 (이름, 유형, 거리, 대표 정보, 출처)

**FR-04 VLM 후보 판별·확신도 산출 (M)**
- 입력: 방문지 대표 사진 1장(축소), 후보 장소 목록과 대표 정보
- 처리: VLM이 후보 중 한 곳을 고르고 확신도(0~1)와 판단 근거를 반환한다. 후보 목록 밖의 장소는 답할 수 없다(8장 AIR-02).
- 출력: 선택 장소 ID, 확신도, 판단 근거 문장
- 라우팅: 확신도 0.8 이상 자동 확정 / 0.5~0.8 사용자 확인 / 0.5 미만 사용자 선택 (임계값은 PoC 후 조정). 후보가 없을 때의 반경 확대는 FR-03을 따른다(8.3 참고)

**FR-05 사용자 확인·수정 (M)**
- 입력: 확인이 필요한 방문지
- 처리: 사진, 후보 목록, AI 추천과 판단 근거를 보여 주고 사용자가 고르게 한다. 목록에 없으면 직접 검색하거나 "기타 장소"로 저장한다. 자동 확정된 방문지도 사용자가 나중에 바꿀 수 있다.
- 출력: 방문지 상태 갱신(확정/기타장소, DR-02), 사용자 확정 결과를 정확도 측정용 매칭 로그(DR-09)로 저장

**FR-06 위치 없는 사진 처리 (S)**
- 입력: GPS가 없는 사진
- 처리: 촬영 시각이 앞뒤 방문지 사이에 있으면 해당 방문지를 추천한다(시간 보간). 시각도 애매하면 VLM으로 인접 방문지 사진과 비교해 추천한다.
- 출력: 추천 방문지와 이유. 최종 배정은 사용자가 확인한다.

**FR-07 지도 동선·타임라인 (M)**
- 입력: 확정된 방문지 목록
- 처리: 카카오맵 위에 방문 순서대로 핀과 경로를 그리고, 방문지 사이 이동 시간을 계산해 타임라인으로 보여 준다. 날짜별·전체 보기를 전환할 수 있다.
- 출력: 동선 지도, 방문지 카드 목록, 타임라인

**FR-08 장소 상세 (S)**
- 입력: 사용자가 누른 방문지
- 처리: 공식 데이터의 장소 개요, 주소, 대표 사진, 출처, 갱신일을 보여 준다.
- 출력: 장소 상세 화면

**FR-09 근거 기반 여행기 생성 (M)**
- 입력: 확정된 방문지, 장소 공식 정보, 사용자가 고른 문체(블로그형 등)
- 처리: LLM에 확정된 사실만 넣어 여행기를 생성한다. 장소 이름은 확정된 장소 ID와 연결하고, 사실 문장마다 출처 각주를 붙인다. 날짜별 동선 요약을 자동으로 넣는다.
- 출력: 제목, 본문, 각주 목록, 동선 요약이 포함된 여행기

**FR-10 문단 다시 쓰기·사실 대조 경고 (C)**
- 입력: 사용자가 고른 문단, 편집한 문장
- 처리: 선택한 문단만 다시 생성한다. 사용자가 편집한 문장 중 공식 데이터와 다른 사실(운영시간, 위치 등)이 있으면 경고한다.
- 출력: 수정된 문단, 경고 표시

**FR-11 공유 카드 생성 (S)**
- 입력: 완성된 여행기
- 처리: 대표 사진, 제목, 동선 요약으로 공유용 이미지를 만든다. 좌표·정확한 위치 정보는 넣지 않는다.
- 출력: 저장·공유 가능한 이미지 파일

**FR-12 근처 못 가본 곳 추천 (C)**
- 입력: 확정된 방문지
- 처리: 방문지 주변의 공식 데이터 장소 중 이번 여행에서 가지 않은 곳을 거리순으로 골라 다음 부산 여행 장소로 안내한다.
- 출력: 방문지별 추천 장소 2~3곳 (이름, 유형, 거리, 출처)

## 8장. AI 요구사항

### 8.1 AI의 역할 범위
AI는 두 가지만 맡는다. (1) 후보 중 사진과 맞는 장소 판별(VLM), (2) 확정된 사실로 여행기 문장 작성(LLM). 그 밖의 처리(EXIF, 군집화, 후보 검색, 확신도 라우팅, 이동 시간, 각주 연결, 사실 대조)는 코드로 구현해 결과를 재현·테스트할 수 있게 한다.

### 8.2 AI 요구사항
| ID | 요구사항 | 관련 FR |
|---|---|---|
| AIR-01 | VLM 입력은 방문지 대표 사진 1장(축소본)과 후보 장소 목록(이름, 유형, 거리, 개요, 대표 사진)으로 한다 | FR-04 |
| AIR-02 | VLM은 후보 목록 안에서만 고르고, 맞는 후보가 없으면 "없음"을 답한다. 응답은 장소 ID, 확신도(0~1), 판단 근거가 담긴 정해진 JSON 형식이어야 한다 | FR-04 |
| AIR-03 | 응답의 장소 ID가 후보 목록에 없거나 형식이 틀리면 코드가 거부하고 1회 재요청한다. 다시 실패하면 사용자 선택으로 넘긴다(8.3) | FR-04, FR-05 |
| AIR-04 | VLM은 사진 속 인물을 분석하거나 설명하지 않는다 | FR-04 (NFR-04) |
| AIR-05 | LLM 여행기에는 확정된 방문지와 공식 데이터만 근거로 넣고, 문장마다 근거 장소 ID를 표시하게 한다 | FR-09 |
| AIR-06 | 생성된 여행기의 장소 ID·사실을 코드가 입력 데이터와 대조하고, 근거 없는 사실 문장은 경고 표시하거나 제거한다 | FR-09, FR-10 |
| AIR-07 | AI 호출 비용을 줄이기 위해 방문지당 대표 사진 1장만 보내고, 이미지는 축소해 전송한다 | FR-04 |
| AIR-08 | 프롬프트는 버전을 붙여 저장소에서 관리하고, 테스트셋으로 매 스프린트 매칭 정확도를 측정한다. AI 도움 범위는 README에 날짜별로 기록한다 | 전체 |

### 8.3 확신도 라우팅
| 확신도 | 처리 | 사용자에게 보이는 것 |
|---|---|---|
| 0.8 이상 | 자동 확정 | 확정됨 표시 (나중에 수정 가능) |
| 0.5 ~ 0.8 | 사용자 확인 | AI 추천 + 판단 근거 |
| 0.5 미만 · VLM 응답 오류 2회 | 사용자 선택 | 후보 목록, 직접 검색, 기타 장소 |
| 후보 없음 | 반경 300m → 600m 확대 재검색(FR-03). 그래도 없으면 사용자 선택 | 직접 검색, 기타 장소 |

방문지 상태(DR-02)는 분석중 → 자동확정 / 확인필요 / 선택필요 → 확정 또는 기타장소 순서로 바뀐다. 자동확정된 방문지도 사용자가 수정하면 확정이 된다.

## 9장. 인수 기준

형식: 조건(Given) → 행동(When) → 결과(Then). 시연 시나리오는 "팀원이 촬영한 부산 1박 2일 사진 24장"을 기준으로 한다.

| ID | 대상 | 인수 기준 |
|---|---|---|
| AC-01 | FR-01 | 사진 24장(위치 있음 21, 없음 3)을 올리면 → 위치 있음 21장·없음 3장으로 정확히 표시된다. 31장을 고르면 업로드가 막히고 안내가 나온다 |
| AC-02 | FR-02 | 시연 사진을 분석하면 → 정답 라벨과 같은 개수의 방문지(6곳)로 묶이고 날짜별로 나뉜다 |
| AC-03 | FR-03 | 방문지마다 → 반경 300m(없으면 600m) 안의 공식 데이터 후보가 표시되고, 각 후보에 출처가 있다 |
| AC-04 | FR-04 · NFR-02 | 팀 테스트셋 30장으로 매칭하면 → 정답과 일치하는 비율이 80% 이상이다 |
